# Процедурные макросы в Rust: разбор

Твой рабочий пример (`o_092`) — правильная структура: `proc-macro = true` в `Cargo.toml`, реализация в `lib.rs`, использование через `use o_092::Hello` в `main.rs`. Разберём три вида и уточним конспект.

## Три вида процедурных макросов

| Вид | Атрибут | Вызов | Назначение |
|-----|---------|-------|------------|
| **Derive** | `#[proc_macro_derive(Name)]` | `#[derive(Name)]` | добавить impl к структуре/enum |
| **Attribute** | `#[proc_macro_attribute]` | `#[my_attr]` на элементе | модифицировать/заменить элемент |
| **Function-like** | `#[proc_macro]` | `my_macro!(...)` | заменить вызов на код |

Все три принимают `TokenStream` и возвращают `TokenStream`.

## 1. Derive — твой пример

```rust
#[proc_macro_derive(Hello)]
pub fn hello(input: TokenStream) -> TokenStream {
    let ast: syn::DeriveInput = syn::parse(input).unwrap();
    let name = &ast.ident;
    quote! {
        impl #name {
            fn hello() {
                println!("hello from {}", stringify!(#name));
            }
        }
    }.into()
}
```

- Вход: **вся структура** (`struct Person { ... }`), а не только имя.
- `syn::DeriveInput` — AST структуры/enum.
- Выход: код, который **добавляется** к исходному (исходный не заменяется).
- Имя макроса (`Hello`) и имя функции (`hello`) могут различаться.

Важное ограничение: derive **не может** модифицировать саму структуру, только добавить код рядом.

## 2. Attribute

```rust
#[proc_macro_attribute]
pub fn my_attr(attr: TokenStream, item: TokenStream) -> TokenStream {
    // attr — то, что внутри #[my_attr(...)]
    // item — элемент, на который навешен атрибут
    item  // вернуть без изменений = «пропустить»
}
```

Вызов:

```rust
#[my_attr]
fn foo() { ... }

#[my_attr(extra, args)]
struct Bar { ... }
```

- **Два входа**: `attr` (аргументы атрибута) и `item` (элемент).
- Может **заменить** элемент целиком, вернув другой код.
- Может вернуть пустой `TokenStream`, чтобы **удалить** элемент.

Пример: `#[test]`, `#[tokio::main]` — attribute-макросы.

## 3. Function-like

```rust
#[proc_macro]
pub fn make_thing(input: TokenStream) -> TokenStream {
    // input — токены внутри make_thing!(...)
    quote! { /* ... */ }.into()
}
```

Вызов:

```rust
make_thing!(a, b, c);
```

- Один вход — токены внутри вызова.
- Похож на `macro_rules!`, но **полный контроль** над токенами и возможность сложной обработки.

## Что уточнить в конспекте

### `proc-macro-error` — актуальность

Твой конспект упоминает `proc-macro-error`. Стоит знать:

- Крейт **архивный** (deprecated), автор рекомендует перейти на `proc-macro-error2` или на встроенные `syn::Error` + `compile_error!`.
- В современном Rust **штатный способ** — `syn::Error`:

```rust
let ast: syn::DeriveInput = syn::parse(input).map_err(|e| e.to_compile_error())?;
```

`to_compile_error()` возвращает `TokenStream` с `compile_error!("...")`, который компилятор покажет с правильной позицией. Этого достаточно для большинства случаев.

### «Полный Rust компилятор как зависимость»

Это неточная формулировка. Процедурный макрос — это **отдельный крейт**, который компилируется в **динамическую библиотеку** и загружается компилятором во время сборки. Он не «полный компилятор», но:

- компилируется **до** основного крейта;
- работает на уровне **токенов/AST**, а не машинного кода;
- увеличивает время сборки, потому что добавляет отдельный крейт + `syn` (который сам по себе большой).

Точнее: «proc-макрос — это отдельный крейт, который компилятор собирает и загружает как плагин во время сборки; плюс `syn`/`quote` — тяжёлые зависимости, отсюда рост времени сборки».

## Практические правила

1. **Не злоупотребляй.** `macro_rules!` покрывает 80% случаев. Proc-макросы — когда нужен доступ к AST (разбор структуры, генерация impl по полям).
2. **`syn` с `features = ["full"]`** — только если нужно парсить выражения/паттерны. Для derive часто достаточно `features = ["derive"]` (меньше зависимостей, быстрее сборка).
3. **Ошибки — через `syn::Error` + `to_compile_error()`**, а не `unwrap()`. `unwrap()` в макросе даёт панику компилятора вместо понятной диагностики.
4. **Тестируй через `proc-macro2`**: вынеси логику в функцию, принимающую `proc_macro2::TokenStream`, и тестируй её обычными unit-тестами.
5. **`cargo expand`** — главный инструмент отладки: показывает, во что развернулся макрос.

## Итог

- Три вида: derive (`#[derive]`), attribute (`#[attr]`), function-like (`mac!()`).
- Все принимают/возвращают `TokenStream`; `syn` парсит, `quote!` генерирует.
- Derive **добавляет** код, attribute **заменяет/модифицирует** элемент, function-like **заменяет** вызов.
- `proc-macro2` — для тестов и не-компиляторного контекста.
- `proc-macro-error` устарел; используй `syn::Error` + `to_compile_error()`.
- Рост времени сборки — из-за отдельного крейта + тяжёлых `syn`/`quote`, а не «полного компилятора».
- Применять, когда `macro_rules!` не хватает: нужен AST, разбор полей, генерация по структуре.
